# 2026-09-10 Gate trailing activation and ledger repair

Base: main at `87483914d5c9c19f61b86361a63597c79d88cdc3`.

## Behavioral changes

- Both polling and WebSocket risk handlers activate only when **current**
  finite profit meets the current positive activation threshold. An earlier
  0.55% best cannot activate a currently -1.12% position when the threshold
  falls to 0.50%.
- `best_profit_pct` remains diagnostic history. New runtime field
  `trailing_peak_profit_pct` starts at valid activation, advances independently,
  and supplies both software drawdown and server protective-stop calculations.
  Activation and initial peak assignment happen under the same state lock.
- Already-active trailing protection is sticky even below zero profit or
  after the activation threshold rises. Hard loss stops remain independent.
- New snapshots persist the active peak. Old already-active snapshots retain
  their existing protection using the old peak; old inactive snapshots cannot
  retrospectively activate. Confirmed cycle resets and direction changes clear
  the active peak. Do not delete runtime files to upgrade.
- The server-stop target floor no longer vetoes an otherwise positive target
  at the activation boundary. The trigger cushion shrinks for small profits.
  A positive *gross* target does not guarantee positive proceeds after fees,
  funding, price rounding, market gaps or execution slippage.

## Accounting

CCXT `amount` remains a magnitude for compatibility. Use `signed_amount` for
accounting, with `sign_resolved` and `sign_source` recording the evidence.
The snapshot now preserves `direction`, `info`, `raw_type`, IDs and missing
balance values. Gate raw `pnl` and `fund` must not be lost through CCXT's
generic `trade` and `fee` categories.

The dashboard reports signed price PnL, signed funding, signed trading fees
and their net sum separately. Transfers and other currencies are excluded.
Legacy records are recovered from trustworthy direction/raw change/matching
balance delta only. Unrecoverable signs or types are visibly marked incomplete,
not counted as wins. Newly fetched exchange rows replace the recent snapshot;
this patch does not invent or overwrite historical exchange settlements.

The existing fetch remains capped at 80 ledger entries. A snapshot that does
not reach 24 hours back is explicitly labelled partial; this is not a full
paginated historical reconciliation service. Net ledger totals in a time
window are cash flows, not necessarily matched completed-trade-cycle returns.

## Unchanged configuration and operational limits

No keys, live configuration, leverage, entry sizing, layer schedule or
`max_loss_pct` value were changed. `max_loss_pct=0.5` means a 50% position
return stop, NOT 0.5%; `0.005` means 0.5%. Startup output and loss logs now
show the actual percentage explicitly. This return includes leverage and is
not a percentage of total account equity.

This is a source repair, not a live deployment, profitability guarantee or
complete audit of all execution risks. Existing active-position changes still
follow the original strategy; the repaired epoch prevents pre-activation
history (including earlier layers) from being used as an active trailing peak.

## Validation and deployment

Run from the repository root in its existing dependency environment:

```sh
python -m pytest -q tests --tb=short
```

The regression tests use fake exchange operations, and one test calls the real
CCXT Gate parser without credentials or network requests. They cover the
reported stale-peak incident, exact-threshold activation, subsequent drawdown,
negative-profit exits after valid activation, concurrent activation, restart
migration, reset, invalid values, server-stop arming, signed losses, fees and
funding, unknown legacy records and partial history.

Before deploying to the actual running bot, back up configuration/runtime,
inspect local uncommitted changes, ensure only one bot instance is running,
and review actual stop settings. Preserve remote protective orders and runtime
identity. Pull the tested main revision with `git pull --ff-only`; do not use
a destructive reset. A running Python process does not load source changes
until a controlled restart. This repair does not restart or trade the account.
